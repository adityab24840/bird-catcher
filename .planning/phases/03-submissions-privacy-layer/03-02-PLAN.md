# Plan 03-02: Security Rules — Firestore + Storage + Emulator Tests (Wave 2)

**Goal:** Extend Firestore rules to cover the `entries` and `submissions` subcollections with deny-by-default client writes and partner-read blocked until `status == 'revealed'`. Replace the Storage placeholder rules with a full path-scoped rule that uses `firestore.get()` for cross-service membership and reveal checks. Write emulator rule tests for every SEC-04 deny and allow scenario.

**Depends on:** 03-01 (`submitEntry` function defines the data model; 03-00 creates the `tests/rules/` directory and `test:rules` npm script)

**Critical pitfall — must check before writing:**
- Firestore rules use `$(database)` variable: `get(/databases/$(database)/documents/...)`
- Storage rules use literal `(default)` string: `firestore.get(/databases/(default)/documents/...)`
- These are NOT interchangeable — mixing them causes silent rule denial in production

    Entry doc rule (`match /pairs/{pairId}/entries/{entryDate}`):
    - `allow read`: if `request.auth != null` AND `request.auth.uid in get(/databases/$(database)/documents/pairs/$(pairId)).data.members`
    - `allow write: if false` — no client writes; Admin SDK only (SEC-02)

    - `allow read` (owner branch): if `request.auth != null && request.auth.uid == uid`
    - `allow read` (partner post-reveal branch): separate `allow read` rule — if `request.auth != null` AND `request.auth.uid != uid` AND `request.auth.uid in get(/databases/$(database)/documents/pairs/$(pairId)).data.members` AND `get(/databases/$(database)/documents/pairs/$(pairId)/entries/$(entryDate)).data != null` AND `get(/databases/$(database)/documents/pairs/$(pairId)/entries/$(entryDate)).data.status == 'revealed'`
    - `allow write: if false` — Admin SDK only (SEC-02)

    The null-guard (`get(...).data != null`) is mandatory: `firestore.get()` on a missing document returns a resource with `.data == null`. Without the guard, accessing `.status` on a null data object would produce a rule error that evaluates to `false` (deny) — which is actually safe but creates confusing deny behavior in tests. Explicit null-guard is clearer and follows defensive correctness.

    Path format inside Firestore rules: `$(database)` is injected by the Firestore rules runtime. The outer `match /databases/{database}/documents` block is already present in the file — the new rules nest under it.

  <action>
    Fully replace the contents of `shared-reveal/storage.rules` with the new rules. The Phase 1 placeholder (deny-all `match /{allPaths=**}`) is replaced but a new deny-all default is kept as the FIRST rule inside the outer match block, followed by the specific pair photo rule.

    Structure of the new `storage.rules`:
    ```
    rules_version = '2';
    service firebase.storage {
      match /b/{bucket}/o {

        // Deny all by default — explicit rules below grant narrow access
        match /{allPaths=**} {
          allow read, write: if false;
        }

        match /pairs/{pairId}/entries/{entryDate}/{uid}/{filename} {
          allow write: ...
          allow read: ...
        }
      }
    }
    ```

    Write rule (`allow write`):
    - `request.auth != null`
    - `request.auth.uid == uid` — owner can only write to their own path
    - `firestore.exists(/databases/(default)/documents/pairs/$(pairId))` — pair must exist
    - `request.auth.uid in firestore.get(/databases/(default)/documents/pairs/$(pairId)).data.members` — must be a pair member

    Read rule (`allow read`):
    - `request.auth != null` AND (
      - `request.auth.uid == uid` — owner reads own photo at any time
      - OR: `request.auth.uid in firestore.get(/databases/(default)/documents/pairs/$(pairId)).data.members` AND `firestore.exists(/databases/(default)/documents/pairs/$(pairId)/entries/$(entryDate))` AND `firestore.get(/databases/(default)/documents/pairs/$(pairId)/entries/$(entryDate)).data.status == 'revealed'`
    )

    CRITICAL: All `firestore.get()` and `firestore.exists()` paths in Storage rules use the literal string `(default)` — NOT the `$(database)` variable. This is distinct from Firestore rules syntax. Using `$(database)` in Storage rules will silently evaluate to false in production.

    The `firestore.exists()` guard before the read-after-reveal `firestore.get()` on the entry doc prevents null-deref when the entry doc does not yet exist.
  </action>

    - Read rule contains owner branch (`request.auth.uid == uid`) and partner-post-reveal branch
