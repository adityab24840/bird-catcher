# Plan 03-01: Server Layer — submitEntry Cloud Function (Wave 1)

**Goal:** Add the `submitEntry` v2 `onCall` Cloud Function to `functions/src/index.ts`. The function validates input with a Zod 4 schema, derives `pairId` from the server-side user document (never from client payload), writes the submission subcollection document, and updates the entry document — all inside a single Firestore transaction with all reads before all writes.

**Depends on:** 03-00 (types `EntryDoc` and `SubmissionDoc` defined; tests confirm Zod schema shape)

  <action>
    Append `export const submitEntry = onCall(callableOptions, async (request) => { ... })` to `shared-reveal/functions/src/index.ts` after the `joinPair` export.

    Implementation steps in order:

    **1. Auth guard** (identical to joinPair):
    - `if (!request.auth) throw new HttpsError('unauthenticated', 'Must be signed in')`

    **2. Zod parse**:
    - `const parsed = SubmitEntrySchema.safeParse(request.data)`
    - `if (!parsed.success) throw new HttpsError('invalid-argument', 'Invalid submission data')`
    - Destructure `{ entryDate, text, photoURL }` from `parsed.data`
    - `const uid = request.auth.uid`

    **3. Firestore ref setup** (refs created before transaction, pairId resolved inside transaction):
    - `const db = getFirestore()`
    - `const userRef = db.doc(\`users/${uid}\`)`
    - Note: `entryRef` and `submissionRef` are constructed INSIDE the transaction after `pairId` is read from user doc — do NOT accept `pairId` from `request.data`

    **4. Firestore transaction** — ALL READS BEFORE WRITES (Admin SDK constraint; see joinPair lines 127):
    ```
    await db.runTransaction(async (tx) => {
      // READ 1: user doc (to get server-side pairId)
      const userSnap = await tx.get(userRef)
      if (!userSnap.exists) throw new HttpsError('not-found', 'User not found')
      const userData = userSnap.data()!
      if (!userData.pairId) throw new HttpsError('failed-precondition', 'You are not in a pair yet')
      const pairId: string = userData.pairId

      // Build refs using server-validated pairId
      const entryRef = db.doc(`pairs/${pairId}/entries/${entryDate}`)
      const submissionRef = db.doc(`pairs/${pairId}/entries/${entryDate}/submissions/${uid}`)

      // READ 2: entry doc (may not exist on first submission)
      const entrySnap = await tx.get(entryRef)

      // IDEMPOTENT GUARD (SUBM-04 / D-08): check BEFORE writes
      const existingMembers: string[] = entrySnap.exists
        ? (entrySnap.data()!.submittedMembers ?? [])
        : []
      if (existingMembers.includes(uid)) {
        throw new HttpsError('already-exists', 'You have already submitted today')
      }

      // WRITE 1: submission subcollection doc
      tx.set(submissionRef, {
        uid,
        photoURL: photoURL ?? null,
        text: text ?? null,
        submittedAt: FieldValue.serverTimestamp(),
      })

      // WRITE 2: entry doc — branch on existence (tx.update on non-existent throws)
      if (!entrySnap.exists) {
        // First submission: create entry in one_submitted state directly
        tx.set(entryRef, {
          pairId,
          date: entryDate,
          status: 'one_submitted',
          submittedMembers: [uid],
          createdAt: FieldValue.serverTimestamp(),
          updatedAt: FieldValue.serverTimestamp(),
        })
      } else {
        // Entry exists (second submission): update via arrayUnion
        tx.update(entryRef, {
          submittedMembers: FieldValue.arrayUnion(uid),
          status: 'one_submitted',  // Phase 3: stays one_submitted; Phase 4 adds reveal logic
          updatedAt: FieldValue.serverTimestamp(),
        })
      }
    })
    ```

    **5. Return**:
    - `return { entryDate, alreadySubmitted: false }`

    CRITICAL constraints to enforce:
    - `pairId` is derived from `userSnap.data()!.pairId` — never from `request.data`
    - `entryRef` and `submissionRef` are constructed after `pairId` is resolved (inside transaction)
    - Both `tx.get()` calls complete before any `tx.set()` or `tx.update()` — the second `tx.get(entryRef)` happens after `pairId` is known, which is fine as long as no writes happen before both reads resolve
    - NEVER call `tx.update(entryRef, ...)` when `!entrySnap.exists` — use `tx.set()` for the first submission
    - Phase 3 does NOT implement auto-reveal: `status` stays `'one_submitted'` regardless of how many members have submitted; Phase 4 will add reveal logic
  </action>
